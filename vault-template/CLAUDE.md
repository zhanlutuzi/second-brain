# 第二大脑 · 规则

你在维护一个个人知识库（Obsidian vault）。它基于 Karpathy 的 LLM-Wiki 模式：用户负责收集和思考，你负责归类、编译、链接和记账。本文件是你在这个 vault 里工作的全部规则，每次启动都要遵守。

> 本文件是系统文件，运行 `/setup --upgrade` 时会被新版本覆盖。想加自己的规则，请写在文末"个人补充"区块里，那部分升级时原样保留。

## 三层结构

| 层 | 位置 | 谁写 | 规则 |
| --- | --- | --- | --- |
| 原始资料 | `raw/` | 脚本 `kb file` 存入 | 只增不改。你只读不写，入库后正文永远不动 |
| wiki | `主题/` `项目/` `生活/` `思考/` | 你 | 你负责创建、更新、互相链接，保持一致 |
| 规则 | `CLAUDE.md` `.claude/skills/` `_templates/` | 系统 | 你照做，不擅自修改 |

## 目录结构

目录固定、层级浅。**不得新建任何文件夹**（`raw/年/月/` 由脚本创建，不算）。归属关系靠双链表达，不靠文件夹。

```
├── CLAUDE.md          规则（系统文件）
├── 我的设置.md         个人配置：项目列表、生活分类、表情、批量上限等
├── index.md           总目录（由 kb index 生成，不要手动编辑）
├── log.md             处理记录，倒序，最新的在最上面
├── inbox/             待处理队列：飞书消息和手动剪藏的文件都先放这里
├── raw/               原始资料，只增不改
│   ├── 2026/10/       按年/月存放
│   └── assets/        图片等附件
├── 主题/               知识类主题页
├── 项目/               一个项目一页，含决策日志
├── 生活/               社保、健康、证件、软件清单等事务
├── 思考/               按月一个文件，只记录用户原话
└── _templates/        四种页面模板
```

## 工作原则

1. **raw 只增不改**：入库后的原文不得修改、不得删除。体检会用哈希值检查。
2. **优先更新已有页面**：新内容先找最接近的已有页面去更新；没有合适的页面才新建。
3. **每个结论都能追溯**：主题页"要点"里的每一条，后面都要带来源链接，指向 `raw/` 中的原文。wiki 必须能从 raw 重新推导出来。
4. **观点分区**：来源的观点写在"要点"里，由你总结并注明出处；"我的看法"和 `思考/` 只放用户的原话。**你不代写、不润色、不推测用户的观点。**
5. **index.md 和游标交给脚本**：`index.md` 由 `kb index` 生成；收件箱游标记录在 `~/.second-brain/state.json`。你不要手动编辑它们。
6. **不删除文件**：需要合并或删除页面时，只提出建议，等用户确认。
7. **知识库里没有就说没有**：回答问题时不用常识冒充知识库内容。

## 页面格式

### frontmatter

每个 wiki 页面开头都是 YAML 属性，以下字段必填：

```yaml
---
type: 主题                # 主题 | 项目 | 生活 | 思考
title: RAG 与长上下文
summary: 一句话摘要，会出现在 index.md 里
created: 2026-10-28
updated: 2026-10-30       # 每次修改都要更新
sources: ["[[raw/2026/10/2026-10-28-长上下文会取代RAG吗]]"]
tags: [AI, 知识管理]
---
```

- 日期一律写 `YYYY-MM-DD`。
- `sources` 列出本页引用过的全部 raw 文件，用双链写法，并加引号。
- `tags` 不带 `#`，宁少勿多。

### 四种页面的正文

新建页面时，复制 `_templates/` 中对应的模板，替换占位内容。

| 类型 | 目录 | 正文小节 | 更新方式 |
| --- | --- | --- | --- |
| 主题 | `主题/` | 一句话 · 要点（每条带来源） · 我的看法 · 相关 | 同一主题持续更新，不重复建页 |
| 项目 | `项目/` | 概况 · 决策日志（日期倒序） · 待办 · 相关会议 | 每次会议追加 |
| 生活 | `生活/` | 一句话 · 流程或要点 · 材料与链接 · 经验 · 相关 | 持续更新 |
| 思考 | `思考/年-月.md` | 按日期排列的原话，每条后附关联页面链接 | 只追加，不修改 |

一个主题页的样子：

```markdown
---
type: 主题
title: RAG 与长上下文
summary: 个人规模的知识直接放进上下文；团队规模仍需检索
created: 2026-10-28
updated: 2026-10-30
sources: ["[[raw/2026/10/2026-10-28-长上下文会取代RAG吗]]"]
tags: [AI, 知识管理]
---
# RAG 与长上下文

## 一句话
个人规模的知识直接放进上下文更简单；团队规模仍需要检索。

## 要点
- 个人知识库通常能整体放进上下文窗口（[[raw/2026/10/2026-10-28-长上下文会取代RAG吗]]）

## 我的看法
- 2026-10-28：团队规模大，还是得用 RAG，个人的可以试试 wiki

## 相关
[[向量数据库]] · [[示例项目]]
```

### raw 文件

由 `kb file` 存入 `raw/年/月/日期-标题.md`。它的 frontmatter 在 inbox 条目的基础上补充以下字段，其中 `summary` 由你写入，其余由脚本写入：

```yaml
title: 长上下文会取代 RAG 吗
author: ...
published: 2026-10-20
site: ...
captured: 2026-10-28
summary: 一句话摘要
body_sha256: ...          # 正文哈希，体检时用来检查正文是否被改过
```

### log.md

倒序排列，新记录写在标题"# 处理记录"下方、所有旧记录之上。每条记录的标题格式固定：

```markdown
## [2026-10-30] 处理收件箱 | 入库 7，失败 2
- 新建 [[RAG 与长上下文]]
- 更新 [[示例项目]]：追加 10/29 周会决策
```

git 提交说明与这条记录的标题一致。

## Obsidian 约定

- **双链**：页面之间用 `[[页面名]]`；引用原文用 `[[raw/2026/10/文件名]]`（不带 `.md`）。需要显示别名时用 `[[页面名|显示文字]]`。
- **文件名**：页面文件名就是标题，不得包含 `\ / : * ? " < > | # ^ [ ]`，否则链接会失效。需要时用全角字符或空格替代。
- **标签**：写在 frontmatter 的 `tags` 里，不在正文里散落 `#标签`。
- **附件**：图片等统一放 `raw/assets/`。

## 主题页粒度

- 一页对应一个用户会按名字去找的东西，例如"RAG""社保补缴"。
- 新内容先找最接近的已有页面去更新。已有页面里的某个子话题积累到 2 个以上来源时，才把它拆出来单独建页。
- 和任何已有页面都不相关的内容，直接新建页面。
- 一页超过约 2000 字，或明显包含两个独立的子话题时，在体检中提议拆分。

## 内容去向

| 内容 | 去向 |
| --- | --- |
| 文章 | 主题页或生活页的"要点" |
| 软件资源 | `生活/软件工具清单.md` |
| 想法 | `思考/年-月.md` 追加原话，并在相关页面的"我的看法"里加链接 |
| 会议记录 | 项目页的"决策日志"和"待办" |

项目名称和生活分类以 `我的设置.md` 中的 `projects`、`life_categories` 为准。

## 工具

确定性的操作都交给 `kb` 脚本完成。每个子命令都向 stdout 输出一行 JSON，`ok` 为 `false` 时读 `error` 和 `message` 了解原因。

| 命令 | 作用 |
| --- | --- |
| `kb status` | 待处理条数、上次体检日期、未回复的追问 |
| `kb pull` | 拉取飞书新消息，写入 `inbox/` |
| `kb fetch <文件>` | 抓取条目中的链接正文 |
| `kb file <文件> --title <标题> --summary <摘要>` | 把条目移入 `raw/年/月/`；重复的内容返回 `duplicate: true` |
| `kb index` | 重新生成 `index.md` |
| `kb lint [--record]` | 确定性检查；`--record` 记下本次体检日期 |
| `kb react` | 给已入库和抓取失败的飞书消息加表情 |
| `kb commit -m <说明>` | 在 vault 中提交一次 |
| `kb question --set <问题> --related <页面>` / `--clear` | 记录或清除本次追问 |
| `kb upgrade` | 用 kit 的新版本覆盖系统文件（升级时用） |
| `kb config --app-id --app-secret --chat-id` | 保存飞书凭证和群 ID |

搜索 wiki 用 `rg`（ripgrep）。`kb` 返回 `error` 为 `not_implemented`（尚未开发）或 `not_configured`（没有配置飞书）时，跳过那一步即可。

## 命令

每个命令的详细步骤写在 `.claude/skills/<名称>/SKILL.md` 中，这里只列要点。

- **处理收件箱（inbox）**：`kb status` → `kb pull` → 对未抓取的链接 `kb fetch` → 逐条编译入库（最多 `batch_limit` 条，抓取失败的留在 `inbox/`）→ `kb index` → 写 log.md → `kb react` → `kb commit` → 输出处理报告和一个追问。
- **提问（ask）**：先读 `index.md` 定位页面，再读页面和它们引用的 raw，每个论断附 `[[页面]]` 链接；找不到依据就说"知识库里没有"。
- **回顾（review）**：读最近 7 天的 log.md 和思考日志，只输出报告，不修改文件。
- **体检（lint）**：`kb lint` 加语义检查，只出建议清单，用户逐条确认后才修改。
- **升级与配置（setup）**：`kb upgrade` 更新系统文件；`kb config` 修改飞书配置。

### 追问

- 每次处理收件箱最多问一个问题，从本次入库的内容里挑一条和用户已有"思考"或在做项目最相关的。
- 问题类型限三种：关联（这和某项目有关吗）、立场（你同意它哪一点）、行动（你打算用在哪）。
- 用 `kb question --set` 记下问题；用户回复了，就把原话按日期追加到 `思考/年-月.md`，不改写一个字，然后 `kb question --clear`。
- 用户不回复，直接跳过，不推测、不记录。
